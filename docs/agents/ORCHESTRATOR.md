# Job Agent Engineering Orchestrator

The orchestrator routes one development task; it does not claim ownership of every subsystem. Its output is a scoped task contract, a bounded result, and an evidence-based handoff.

1. Restate the user objective and identify product surface. Read `README.md`, the applicable policies, and the relevant current-state leads. For affected trust boundaries or release work, read `audit/AUDIT-STATE.md` and unresolved `audit/AUDIT-FINDINGS.md`; reconcile rather than inherit old conclusions.
2. Before any edit, record `pwd`, `git rev-parse --show-toplevel`, `git branch --show-current`, `git rev-parse HEAD`, and `git status --short`. Confirm remote/canonical repository and whether the worktree is a release candidate, detached, or dirty. Check active ownership in tasks/PRs/worktrees and ask the owner or stop on overlapping files/subsystems. Do not alter another agent's worktree or make a dirty source appear clean.
3. Classify the task as read-only diagnosis, implementation, trust-boundary change, live verification, or release preparation. Fill every field in `TASK_CONTRACT.md`, including actual baseline, exclusions, evidence, approval gates, and loop limit. `UNKNOWN — VERIFY` is acceptable; a guessed success is not.
4. Assign the smallest necessary owner and reviewers from `SPECIALISTS.md`. A role is a responsibility, not an automatic subagent. Keep one writer per subsystem; QA, security, and live verification may review read-only after a change. Use existing `.claude/agents/` helpers only when that environment and task call for them.
5. Select one applicable loop from `LOOPS.md` only if iteration is needed. Count attempts; do not reset a limit by renaming the task, changing agents, or switching worktrees. Preserve the first divergence and each distinct hypothesis. Stop scope expansion and record a new task separately.
6. Require the smallest reversible change and focused regression evidence. For trust-boundary or release work, require the specific database/RLS, tenant, receipt, security, exact-source, and live-path evidence in the existing policies. Request the existing independent auditor's one-cycle handoff at the triggers in `audit/CONTINUOUS-AUDIT-AGENT.md`; build agents cannot edit or close audit findings. Keep unresolved Critical/High IDs in the candidate handoff until independent re-verification supplies the specified regression and hosted evidence; no status disappears because a build passed or PR merged. Local tests, synthetic fixtures, CI, Preview, and Production prove different things.
7. Decide **PASS** only when every acceptance criterion has direct evidence. Decide **BLOCKED** when a required environment, authorization, source, or proof is unavailable, or the loop limit is reached. Decide **NEEDS DECISION** when policies conflict or a product-owner choice is required. Unknown evidence stays unknown.
8. Finish with `docs/AI_HANDOFF.md`'s implementation contract. Reconcile auditor findings through `audit/AUDIT-HANDOFF.md`, record accepted decisions and checkpoint updates separately, and route any fix as a bounded development task. For a release, hand the exact candidate and blockers to the Release Manager; only a human owner may make the production decision.

No unattended polling, self-generated backlog work, or endless development cycles. A task may resume after new evidence or a human decision, with the prior attempt count and handoff preserved.
