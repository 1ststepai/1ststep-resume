# Controlled Job Agent Beta

The customer-facing product is now intentionally focused on the Job Agent. Legacy self-service tools remain in the codebase as internal capabilities but are no longer linked from `/concierge`. See `docs/FOCUSED_JOB_AGENT_BETA.md` for the current access gate and secure employer-authentication handoff.

## Product slice

The Concierge launch at `/concierge` now uses a three-step guided flow:

1. Add or build a resume.
2. Choose a suggested job path or compare paths against connected direct-employer feeds.
3. Tap work setting, employment type, and salary floor, then start the agent.

Free text is optional. Hybrid and on-site searches request a city or commuting area; remote searches default to United States. Subscribers see simple job cards and one **Needs You** queue. The underlying verified-role pipeline, truth profile, reusable-answer vault, document workflow, audit records, and receipt-only submission counting remain intact behind a server-verified admin control.

Saved Info uses a short core setup of 15 reusable facts: contact method, work authorization and sponsorship, employment and education history, skills, compensation and availability, travel and relocation, remote geography and schedule, recruiter-contact preference, optional-demographic default, and exclusions. Resume-derived drafts can prefill the factual history for confirmation. Ten employer-specific or consequential items—including exact address, conflicts, licenses, driving, background or health screening, references, employer-account creation, and employer privacy terms—are deferred until a verified application actually needs them. Secret-shaped values are rejected, optional demographics remain unanswered or “prefer not,” and consequential answers are never silently reused.

Receipt-verified applications retain a separate encrypted post-submission record. The job seeker can confirm Interview or Rejected/Closed and can schedule or complete a seven-day in-app follow-up reminder from the application card. These mutations use optimistic versions, append to the signed application audit chain, never infer an employer decision, never alter the receipt, and never contact an employer. Due reminders also appear in the consolidated **Needs You** queue.

Each scheduled follow-up also atomically creates a tenant-opaque encrypted due record beside the application-session mutation. The hourly heartbeat recovers expired leases and hands due reminders to the existing generic Needs You outbox only when the user opted into email and the reviewed sender is configured. The record and provider payload contain no employer, role, requisition, question, resume, or profile details. Completing, rescheduling, closing, or deleting the application invalidates the due record; the notification worker rechecks current application state immediately before any provider call.

An active run has exactly one subscriber-facing state: **Searching**, **Preparing**, **Waiting for You**, **Paused**, or **Finished**. Slow discovery and AI calls end with saved-progress retry guidance instead of an indefinite loading state. Subscriber autonomy is limited to prepare-only or automatic filling of ordinary verified answers followed by review; no standing “Auto-submit” mode exists, and final submission always requires a separate exact-action confirmation.

Cross-device restore no longer depends on a browser-local run identifier. After opaque-session authentication and Job Agent access verification, a new browser requests the latest encrypted direct-employer discovery run through the tenant-scoped run API, restores its bounded mission and authoritative run state, and caches only the opaque run reference for later polling. Application-package runs are excluded from this convenience restore so private document payloads are never returned by the discovery lookup.

Hydration always resolves the newest tenant discovery run rather than trusting a cached browser reference. This prevents an expired, deleted, or older device run ID from hiding work started elsewhere; an authoritative empty result clears only the obsolete opaque reference and does not invent progress.

Signed users also receive a one-time, four-checkbox authorization step before the first durable Job Agent run. It records only an 18+ attestation, acceptance of the configured Terms version, acknowledgement of the configured Privacy version, and authorization for direct-employer discovery, encrypted confirmed-profile storage, AI document preparation, and the supervised application workspace. It does not collect a date of birth and does not replace employer-specific transmission or final-submission confirmation. The Saved Info screen provides an equally direct revoke control; revocation is saved first and then pauses active runs and application sessions.

Visitors can run guided discovery and narrowly scoped AI helpers before signing in. Guest access has stricter per-IP daily limits (30 discovery requests; 10 concierge, 2 profile-extraction, and 1 resume-generation request) plus shared production budgets. Invalid bearer or opaque-session tokens never fall back to guest access. Signing in is required for encrypted cross-session synchronization, subscriber entitlements, and every admin capability.

## Opportunity-path evidence

`lib/opportunity-paths.js` groups roles into transparent job families. A path rank uses:

- current openings from the connected public employer feeds;
- requisition-to-confirmed-profile fit scores;
- the candidate's own tracked outcomes when enough evidence exists.

Interview and offer rates are not market promises or model-predicted probabilities. The UI derives them from the signed user’s durable tracker: only authoritative employer receipts enter the denominator, and only the user-confirmed Interview action enters the recruiter-screen numerator. A later Rejected/Closed update does not erase an earlier confirmed interview. Duplicate receipt evidence is suppressed. No percentage appears before five applications in the same path; 5–19 is labeled directional and receives only a small ranking weight, while “reliable” requires at least 20. One to four observations are labeled too early, and no sample remains learning. Protected traits are not inputs.

The internal acquisition funnel uses the same receipt rule. With no verified sample it shows that yield is unavailable rather than rendering zero or calculating from unverified tracker labels.

## Local run

```powershell
npm install
npx vercel dev --listen 4179 --yes
```

Open `http://localhost:4179/concierge.html`.

Validation:

```powershell
npm run test:concierge
npm run smoke
npm run test:browser:job-agent
npm run security:gate
```

The security gate is intentionally fail-closed when required production rate-limit and budget variables are absent.

## Release procedure

On Windows, deploy with Vercel's normal remote build after the validation commands pass:

```powershell
npx vercel --prod --yes
```

Do not run `vercel build` followed by `vercel deploy --prebuilt` from this checkout. Vercel's local output can be hardlinked to source files on Windows, so an interrupted or faulty prebuilt upload can mutate the working tree. Record SHA-256 hashes for `index.html`, `app.js`, `concierge.html`, and `concierge.js` before release; compare them after deployment, then verify the deployed JavaScript size, readiness response, authentication boundary, and production alias before accepting the release.

Signed-in beta users receive encrypted, tenant-partitioned campaign metadata sync through `/api/concierge-state`. The synchronized metadata includes run state, job-card progress, Needs You summaries, and operating-contract records. Saves use optimistic versions and idempotency keys, expire after 90 days, and reject resumes, contact details, reusable answers, credentials, OTPs, CAPTCHA content, and other private execution context. The existing device copy remains available when cloud sync is not configured or temporarily unavailable.

The launch includes one checked **Keep searching daily** choice. When production scheduling is enabled, it stores the validated mission in an encrypted tenant schedule and enqueues at most one idempotent direct-employer discovery run per UTC day. Short leases recover abandoned claims, consent is rechecked before every enqueue, revocation pauses the schedule, and a configured global daily cap defers excess work. The due index contains only an opaque tenant HMAC. Scheduling cannot create application sessions, transmit personal data, or submit applications.

`/api/session-capabilities` accepts only the revocable opaque HttpOnly Job Agent session and exposes the internal evidence console only when its server-restored subject is listed in `OWNER_ACCESS_EMAILS`. A legacy bearer token receives `SESSION_UPGRADE_REQUIRED`; a missing, invalid, expired, or ordinary subscriber session fails closed with no admin control rendered. A legacy `essential` or `complete` tier does not imply Job Agent access: the encrypted session must contain an explicit `job-agent-controlled-beta` grant issued under the configured versioned access policy, and the pseudonymous pilot admission check must also pass.

Production requires `TIER_SECRET`, `OWNER_ACCESS_EMAILS`, `RATE_LIMIT_HASH_SECRET`, `BETA_DATA_ENCRYPTION_KEY` (32 bytes, base64 or 64 hex characters), an explicit safe `BETA_DATA_ENCRYPTION_KEY_ID`, and the Upstash Redis REST URL/token. During staged rotation, up to three prior keys may be supplied only through the server-side `BETA_DATA_DECRYPTION_KEYS` JSON keyring; new writes always use the active ID. The signed beta additionally fails closed unless `JOB_AGENT_CONSENT_ENFORCEMENT=true`, `JOB_AGENT_COUNSEL_APPROVED=true`, and reviewed versions are set for `JOB_AGENT_TERMS_VERSION`, `JOB_AGENT_PRIVACY_VERSION`, and `JOB_AGENT_AUTHORIZATION_VERSION`. Daily background search additionally requires `JOB_AGENT_SCHEDULE_ENABLED=true` and an explicitly approved `JOB_AGENT_SCHEDULE_GLOBAL_DAILY_RUNS` value from 1–10,000. Changing any policy version automatically requires reacceptance. Never place secret values in browser code or tracked environment files.
The internal receipt-ingestion route additionally requires `JOB_AGENT_RECEIPT_SECRET` with at least 32 characters. It is a server-only HMAC key used by the isolated worker; ordinary subscribers and browser JavaScript cannot use the route. Authenticated email and ATS API receipt paths additionally fail closed unless the independently verified sender domains or connector providers are configured in `JOB_AGENT_RECEIPT_EMAIL_DOMAINS` and `JOB_AGENT_RECEIPT_API_PROVIDERS`.
Tamper-evident application-session audit entries additionally require the separate server-only `JOB_AGENT_AUDIT_SECRET`. Content-free archived head bundles require a distinct 32-character-or-stronger `JOB_AGENT_AUDIT_EXPORT_SECRET`; production readiness fails closed without it. The admin audit endpoint, including `head=1` downloads, fails closed for every subject not listed in `OWNER_ACCESS_EMAILS`.

Off-session **Needs You** email alerts are optional per user and require `JOB_AGENT_NEEDS_YOU_EMAIL_ENABLED=true`, `RESEND_API_KEY`, a reviewed `RESEND_FROM` identity, the server-only `RESEND_WEBHOOK_SECRET`, and an explicit `JOB_AGENT_EMAIL_SUPPRESSION_TTL_DAYS` from 30 through 730. The encrypted preference stores no recipient address; the signed session supplies it server-side. Messages use fixed generic copy without job or candidate details, carry fixed product and pseudonymous tenant tags, and provider acceptance never advances application state. The raw-body webhook accepts only current Svix-signed `email.bounced` and `email.complained` events correlated to that exact product, sender, recipient-derived tenant HMAC, and event ID. It stores an encrypted suppression reason/reference hash without the email address, rejects replay, and blocks future provider calls before reserving spend. Activation can create provider usage and still requires separate owner approval, sender-domain verification, retained delivery/bounce/complaint fixtures, and cost review.

## Production boundary

The production data plane uses tenant-partitioned encrypted durable records; device-only fallback data remains suitable only for supervised product testing. External submission remains disabled in the supplied environment. The employer workspace supports a value-free `.example.test` development preview and a disabled-by-default remote-stream abstraction. The remote provider, receipt capture, durable submission queue, and scope-bound launch evidence must all be configured and independently verified before execution can become eligible.

Stripe remains the legacy subscription source of truth, but a restored paid tier is not itself a Job Agent entitlement. During the controlled beta, a reviewed `JOB_AGENT_ACCESS_POLICY_VERSION` and `JOB_AGENT_CONTROLLED_BETA_INCLUDED_TIERS` policy may issue an explicit encrypted session grant; the separate pseudonymous pilot allowlist still decides admission. Dedicated Job Agent billing remains disabled, and no access screen creates a checkout or charge. Webhook CRM/notification fulfillment requires a durable Redis lease and completion record keyed by an HMAC pseudonym of the Stripe event ID. Concurrent delivery, serverless restarts, retry release, lease recovery, and completed replay are covered locally; Signed beta cannot become eligible without the separate idempotency secret. A supervised signed Stripe test-event redelivery and downstream duplicate check remain required before pointing the live webhook destination at the candidate deployment.

Before inviting real beta users, production must provide:

1. Exercise the implemented opaque Job Agent session boundary with a supervised real account: expiry, rotation, device loss, current/all-device revocation, restore, and cross-tenant denial. Legacy bearer compatibility remains isolated to the separate resume product and cannot authorize Job Agent subscriber routes.
2. Move the implemented encrypted applicant vault to managed-key rotation and independently exercise the tenant-wide export/deletion control with a supervised real account. The cloud lifecycle endpoint now covers the vault, metadata-only campaign sync, durable runs/packages, application sessions, audit entries, provider-confirmed browser-session teardown, and all device sessions. A provider teardown failure preserves only the unresolved encrypted recovery references and reports truthful partial progress before other records are deleted; device-only browser data remains explicitly separate.
3. Validate the Greenhouse extension path before any cloud browser. Configure the server-only `JOB_AGENT_EXTENSION_HANDOFF_SECRET`, run retained synthetic same-requisition, cross-requisition, blocked-field, partial-fill, expiry, replay, logout/reload, and no-submit fixtures, then record `JOB_AGENT_GREENHOUSE_EXTENSION_APPROVED=true` with a reviewed version. The extension must retain no profile, résumé, auth token, candidate value, or local application status. A real employer test requires separate explicit authorization and employer/ATS terms review.
3. Activate and verify the isolated-worker stages. Direct-employer discovery and role-specific DOCX/PDF package generation use encrypted tenant state, idempotency, leases, heartbeats, bounded retries, pause/resume, terminal failure, immediate execution, and daily recovery. New package generation is bound to the same tenant's finished published direct-employer discovery result; employer, title, requisition, Apply URL, and job text are restored server-side rather than trusted from browser claims. The deny-all document-render adapter and signed persistence path are connected but deliberately disabled until its reviewed snapshot and usage budget are authorized. Needs You notification persistence and the employer-form queue/session boundaries are connected; their external email and remote browser providers remain disabled.

The signed durable application-session API is connected to the subscriber job cards and the single **Needs You** queue. It enforces exact rendered-package identity, tenant isolation, encrypted non-secret checkpoints, masked field references, separate short-lived transmission/submission approvals, optimistic concurrency, and no public receipt mutation. Package edits are new encrypted versions that repeat truth, ATS, artifact, and render gates; they never inherit Package Ready or approval evidence. Encrypted tenant-bound browser-session metadata, resume/end controls, safe expiration, export/deletion, and a no-provider local fixture are implemented. Live employer navigation, interactive field extraction/filling, receipt ingestion, and remote provider-session recovery remain disabled until the isolated worker, employer terms review, recovery drills, and usage budget are explicitly approved.
4. Provision the isolated employer browser adapter. The checked-in fail-closed contract now enforces exact-host navigation, schema-only extraction, ordinary verified-field planning, explicit Human Action Required categories, current transmission approval, no credential/challenge collection, no submission result, and synthetic fixture coverage. It remains disabled until a reviewed snapshot, per-application cookies/storage, bounded employer-only egress, budgets, terms approval, and recovery drills are authorized.
   The launch manifest now reports the remote interactive provider and provider-bound recovery drill as separate blockers. Failed or expired provider sessions retain their encrypted recovery reference until teardown is confirmed; the local fixture cannot satisfy either production gate.

   The initial extension path is deliberately narrower: `npm run build:extension:controlled` creates a reproducible Greenhouse-only no-submit archive from an exact allowlist. Legacy multi-site fillers, unsupported platform claims, remote font stylesheets, and testing assets are excluded. The archive digest is pinned and must be configured exactly before assisted application can become eligible.
5. Connect the existing exact-employer, exact-version action-time approval records to the isolated worker; the subscriber confirmation UI and fail-closed server grants are implemented, but no transmission consumer is enabled.
6. Provision and approve employer-page/email/API receipt capture plus the independent read-only receipt worker. The implementation atomically creates an encrypted receipt task after a submission attempt, restores only exact tenant/browser scope, keeps raw evidence in memory, and sends it through the signed verifier. The verifier checks exact-host page evidence plus the recorded response fingerprint, DKIM/DMARC-authenticated allowlisted email, or signed allowlisted ATS API evidence before persisting a minimized hash/reference record. Bounded evidence checks may resume, but submission never repeats; exhaustion becomes **Verify employer receipt** and remains uncounted. Both live controls remain disabled in the supplied environment.
7. Provision and independently verify the disabled-by-default exact-host retention archive adapter. It accepts only a valid content-free signed head, uses digest-scoped idempotency and approved monetary controls, and requires a provider-signed acknowledgement binding the stored digest, immutable object version, and exact retention deadline. A 2xx response or valid signature alone is not proof of storage enforcement, replication, restore, or legal hold. Retain receiver-side evidence, sign it as the scope-bound `audit-archive` launch artifact, and complete backup/restore and incident-response drills. The current encrypted Redis ledger remains tenant-scoped, atomically append-only, hash-chained, separately HMAC-signed, deletion-aware, and verified by cross-tenant/tamper tests, but Redis is not a regulatory WORM archive.
8. Production rate-limit configuration and cost budgets required by `scripts/production-security-gate.mjs`.
9. Register `/api/job-agent-email-events` as the Resend webhook for permanent bounce and complaint events, retain the endpoint signing secret only in Production scope, and verify one approved synthetic inbox receipt plus signed bounce and complaint fixtures. Confirm the content-free suppression counter increments, the recipient is not retained in the suppression record, a replay is idempotent, a later Needs You event makes no provider call, opt-out remains effective, and provider usage stays within the approved limits. The implementation and one-click UI remain local until this external verification is explicitly authorized; no email or webhook registration was performed while building them.

The controlled beta now also has a fixed-schema, content-free operational counter ledger in Redis and an admin-only two-day view inside the evidence console. It counts invalid authentication and rate-limit exhaustion alongside workflow/provider failures, privacy outcomes, completed provider requests, provider-reported input/output tokens, durable email suppressions, and overdue encrypted account exports; it never stores candidate values, account identifiers, or tenant identifiers. The admin console shows aggregate submission, receipt, account-export, and operator-alert queue health. Hard global weighted-request budgets remain enforced before provider calls. A disabled-by-default HTTPS alert adapter can enqueue only fixed-schema readiness, audit-integrity, safety-control, global-budget, consequential-queue, and account-export-queue events for an exact allowlisted hostname. Redis durably leases and retries each record with a stable idempotency key, then exposes terminal failures in a dead-letter count; alert-channel failures do not recursively enqueue more alerts. No destination is contacted until an operator configures and verifies it. Monetary invoice reconciliation and verified end-to-end alert recovery remain expansion gates rather than inferred telemetry.

Recommended pilot boundary: discovery, direct-source verification, fit ranking, document preparation, and human-reviewed application work for 5–10 supervised users. The versioned consent control is implemented and tested, but policy wording and versions still require counsel approval before invite. Do not advertise unattended submission until the browser worker, employer/ATS review, and live receipt-capture controls are implemented and independently tested.

Operational go/no-go checks, stop conditions, incident triage, candidate data-request handling, and the support script are defined in `docs/JOB_AGENT_BETA_RUNBOOK.md`. The current legal/compliance product rules, official-law signals, required counsel deliverables, and allowed launch claims are in `docs/JOB_AGENT_LEGAL_COMPLIANCE_GUARDRAILS.md`.

Signed-beta readiness also requires the versioned support/incident ownership contract to be explicitly approved, both monitored owners to be assigned, coverage and escalation policy versions to be recorded, and the configured runbook SHA-256 to match the reviewed build. Public and admin-safe readiness expose only booleans and versions, never owner identifiers.

The separate owner launch decision is represented by a 30-day signed `controlled-beta-release` evidence envelope. Its scope binds the reviewed clean commit and runtime digest to the pilot allowlist digest, access and consent versions, schedule limit, actual unit and integer-cent caps, owner digests, alert/notification contracts, and every assisted/submission activation flag. Changing any bound value makes Signed beta ineligible until the new release is reviewed and signed; the envelope never contains account emails, owner addresses, secrets, or candidate values.

A deterministic read-only release-record generator and verifier now sit in front of that signer. They require a clean release preflight, exact commit/runtime equality, production-mode evaluation, and zero remaining Signed-beta blockers other than the release evidence itself. The signing command reruns both checks and will not sign an arbitrary file presented as the release record.
