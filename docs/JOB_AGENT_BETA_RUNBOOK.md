# Job Agent controlled-beta runbook

This runbook is the operator contract for a supervised 5-10 person Job Agent beta. It does not authorize employer-form transmission, account creation, or submission. Those capabilities remain disabled until the isolated worker and action-time controls are separately approved and verified.

## Support and incident ownership contract

Signed-beta eligibility requires a reviewed contract, not an unverified contact string. Assign a monitored support owner and a separately accountable incident owner, then record the reviewed coverage policy, escalation policy, and this exact runbook version. Set `JOB_AGENT_SUPPORT_INCIDENT_APPROVED=true` only after those owners accept their duties and the support coverage and escalation paths are tested. Store owner addresses only in server-side environment values; readiness exposes assignment booleans and versions, never the addresses.

Hash this exact file with SHA-256 after review and set `JOB_AGENT_INCIDENT_RUNBOOK_SHA256` to that digest. The configured digest must match the fingerprint embedded in the reviewed build. Any runbook edit intentionally invalidates readiness until the change is reviewed, the runbook and support/incident contract versions advance as appropriate, and the embedded fingerprint is updated. A matching hash proves configuration binding, not that an owner is monitoring a channel; retain the acceptance and paging-test evidence in the release record.

## Release-bound approval

`JOB_AGENT_CONTROLLED_BETA_APPROVED=true` is not sufficient launch authority. Start from a reviewed clean commit and require `npm run security:release-preflight` to report `ok: true`. Record its exact `runtime.sha256` as `JOB_AGENT_RELEASE_RUNTIME_SHA256` and require the deployed `VERCEL_GIT_COMMIT_SHA` to be the same 40-character commit reviewed by the owner. Never copy either value from an older build or invent one for a local dirty checkout.

Retain a content-free release record covering the commit, runtime digest, pilot size and pseudonymous allowlist, consent/access-policy versions, actual unit and integer-cent caps, support and incident ownership, schedule limit, notification/alert contracts, and every assisted or submission activation flag. From the exact reviewed environment, sign that artifact with `npm run security:sign-launch-evidence -- --kind controlled-beta-release ...` and store the resulting envelope only in `JOB_AGENT_CONTROLLED_BETA_RELEASE_EVIDENCE`. The manifest accepts it for at most 30 days. Any bound configuration, capability mode, owner, cap, policy, allowlist, commit, or runtime change invalidates the evidence and requires a new review; never re-sign merely to clear the blocker.

Generate the record with `node scripts/create-controlled-beta-release-record.mjs` only after the clean preflight passes and the exact commit/runtime environment values are present. The command is read-only, outputs JSON to standard output, and exits nonzero when any other Signed-beta prerequisite remains. Retain the output outside the deployed runtime, inspect it, then run `node scripts/verify-controlled-beta-release-record.mjs --artifact <record.json>` from the unchanged candidate environment. Only after explicit owner review may the existing signing command be run with `--kind controlled-beta-release` and its exact confirmation phrase. That signing path reruns the clean preflight and deterministic verifier and refuses tampered, stale, incomplete, mismatched, or manually fabricated release records. The record includes safe hashes and versions but excludes allowlist values, owner addresses, secrets, and candidate data.

## Launch modes

| Mode | User-visible capability | Allowed now |
| --- | --- | --- |
| Preview | Guided goal, public direct-employer discovery, transparent filtering | Yes |
| Signed beta | Encrypted profile/vault, resumable search, job cards, Needs You, private package generation | Yes, for invited supervised users |
| Package Ready | Downloadable versioned ATS artifacts after deterministic and isolated visual QA | Only after the render sandbox and its budget are explicitly enabled and verified |
| Assisted application | Isolated employer browser, ordinary field fill, credential/challenge pauses | No |
| Final submission | Consequential transmission plus authoritative employer receipt | No |

Never describe a prepared package, a submission attempt, or a candidate statement as Submitted. Only an authoritative employer receipt may advance that state.

The checked-in launch manifest evaluates these modes independently. `/api/job-agent-readiness` returns `readyFor` plus a content-free `launchManifest`; `status: ready` does not imply assisted applications or final submission. The manifest includes a deterministic `actionPlan` that maps every blocker to its earliest launch stage, accountable owner, required proof type, and next safe operator action. The read-only CLI report keeps this concise by returning phase counts, the next action, and the first five actions; the full admin/readiness manifest retains every action. An unknown blocker fails closed with an investigation action rather than being silently ignored. The admin-only evidence console shows the same blockers. Assisted application remains fail-closed until the durable worker, exact snapshot/digest evidence, terms review, owner approval, and a resumable in-app browser-session handoff are all implemented and verified. The authoritative receipt-capture connector is implemented but disabled by default; final submission remains hard-disabled until capture is separately approved, configured, and verified and execution is separately authorized.

## Daily supervised-beta checks

- Read the shallow readiness result and deployment health once per operating day.
- Open the admin-only evidence console and review the two-day content-free operational counters for invalid authentication, rate-limit exhaustion, completed provider requests, provider-reported input/output tokens, provider failures, discovery, durable-run, package, artifact-QA, application-session, submission attempt/expiry/unknown/failure, receipt pending/verified/review/failure, audit-integrity, Needs You notification acceptance/failure/suppression, readiness, and account-data outcomes. A healthy generic heartbeat with missing submission or receipt counters is not evidence those workflows succeeded; reconcile attempts to verified receipts and investigate every outcome-unknown or worker-failure count. A new email suppression must correspond to a retained provider-side bounce or complaint fixture before notification delivery is trusted, without inspecting or copying the recipient address into operational evidence. Pending and candidate-review counts are workload signals, not verified submissions. Durable package generation and the authenticated legacy Claude proxy now contribute their provider-reported tokens to the same ledger. The separate cost-evidence row states that dollar cost is unknown and shows configured global ceilings as weighted request units, not currency. Do not inspect candidate text to diagnose aggregate health. Reconcile these totals to provider billing before expanding beyond the controlled beta; missing provider usage remains unknown, never zero.
- Review the admin-only monetary ledger by category. `reservedCents` is in-flight or reconciliation-required exposure, `settledCents` is the conservative reserved maximum unless a trusted actual amount was supplied, and `releasedCents` is capacity proven unused. Compare all three with provider invoices; a missing or unreliable invoice signal is `unknown`, never zero.
- Require the admin-only background-worker heartbeat to remain `healthy` after each expected hourly window. Treat `incomplete`, `failed`, `stale`, or `unknown` as an investigation signal; compare invocation, enqueue, replay, consent-pause, budget-deferral, and scheduler-failure counters before resuming. Compare scheduled discovery count with `JOB_AGENT_SCHEDULE_GLOBAL_DAILY_RUNS`; stop new schedules if cron health, due-index recovery, or current usage is unknown.
- Review **Operational queues · aggregate only** even when the heartbeat is healthy. Submission `overdue` means queued/leased work is more than two hours beyond its due score; `reconciliation pending` includes both timed-out executions and outcome-unknown records retained until acknowledgment, while `reconciliation due` requires immediate review. Receipt `overdue` means a read-only check is more than two hours past its scheduled retry. Account export `overdue` means an encrypted self-service export has remained due for more than five minutes. Any `attention-required` state sends a cooldown-deduplicated generic operator warning and must be reconciled before expanding the pilot. If queue observation itself fails, the invocation must return HTTP 500, its heartbeat must be `failed`, and the console must show queue state as `unknown`; never treat previous counts as current. These aggregates contain no tenant, employer, application, account, or candidate identifiers and do not prove submission, receipt, export delivery, or candidate impact; inspect an authorized tenant record only through the normal support workflow when investigation is approved.
- If the content-free alert adapter is configured, send controlled synthetic tests for readiness failure, submission outcome unknown, receipt-worker failure, and overdue account export before inviting users and verify receipt at the approved incident endpoint. Force one transient failure and confirm durable retry uses the same idempotency key; force a terminal rejection and confirm the admin-only dead-letter count becomes `attention-required` without recursive alerting. Verify the receiver deduplicates replay of that key. These events never contain employer, account, or candidate details. A configured URL or successful HTTP request alone is not proof that an operator received the alert.

Verify the command succeeds twice with the same SHA-256, inspect `RELEASE-INTEGRITY.json`, and confirm the archive contains only the listed Greenhouse, 1stStep bridge, popup/side-panel, and icon files. Set `JOB_AGENT_GREENHOUSE_EXTENSION_SHA256` to that exact reviewed digest before signing controlled-beta release evidence. Never zip the whole source directory; it contains intentionally excluded legacy and marketing material.
- Run `npm run security:sherlock-review` and retain its content-free seven-category result. In the Greenhouse fixture, confirm only the tenant-owned `resume_pdf` with completed isolated-render evidence is returned, the extension rejects any filename/version/size/MIME/hash mismatch before ordinary fields are filled, no document bytes enter Chrome storage or completion messages, and Submit remains untouched.
- Run `npm run security:environment-shape:summary` inside the protected candidate environment before any readiness drill. This report emits only requirement identifiers and `valid`, `invalid`, or `absent` states; it never emits values, lengths, URLs, or tokens and performs no writes or external calls. Treat it as configuration-shape evidence only. Vercel variable-name listings and local `vercel env run` output are not deployed-runtime proof, especially when a stale `.env.local` is present. The authenticated deployed readiness endpoint plus signed receiver-side drill evidence remains authoritative.

Repeat at Greenhouse handoff and verify the check occurs before applicant-vault restore or approval consumption, the closed session reports no transmission/submission/receipt, and the other queued applications continue.

## Automatic stop conditions

Pause new signed-beta work when any of these occurs:

- readiness is unavailable, audit verification fails, tenant isolation is uncertain, or encryption/signing configuration is missing;
- a provider/global budget is exhausted or current spend cannot be established;
- repeated 401/403 anomalies suggest token theft, cross-tenant access, or origin bypass;
- package text or artifacts contain an unsupported fact, protected-trait ranking, credential, sensitive challenge value, or mismatched requisition/version;
- a dependency, document parser, webhook, or storage incident could affect confidentiality or integrity;
- an employer objects to automation or its terms have not been reviewed for the intended interaction;
- a state is marked Submitted without authoritative employer-side evidence.

Pausing must preserve each encrypted run and application checkpoint when safe. Continue unrelated jobs only when the affected control is not global. Never weaken a safety gate to restore throughput.

## Incident triage

1. Stop the narrowest affected capability. Disable all new beta work if tenant or key integrity may be involved.
2. Preserve content-free logs, deployment ID, timestamps, route/error class, affected opaque record IDs, and signed audit heads. Do not copy candidate values into incident notes.
3. Determine whether confidentiality, integrity, availability, billing, or employer-side action is affected. Mark unavailable evidence unknown.
4. Rotate the affected credential or key through the managed environment. For a staged data-encryption-key rotation, first retain the previous active key under its prior ID, set the new key and new active ID together, run the synthetic drill, deploy, and verify signed-user/vault/run/application lifecycle probes. Do not remove a prior key until its dependent envelopes have expired or been re-encrypted. For suspected key compromise, pause affected work and follow the incident-notification process; rotation cannot undo prior disclosure.
   - Before retiring a prior key, complete the re-encryption dry run and record its final content-free totals/checkpoint.
   - Apply re-encryption only with explicit change authorization, an approved backup, the exact confirmation variable, and bounded batches. Preserve and retry version conflicts; never bypass the CAS guard.
   - Repeat dry mode after apply and require `needsReencryption: 0` before removing the prior key from the managed environment.
5. Verify containment with synthetic probes and cross-tenant negative tests before resuming.
6. Document the root cause, candidate impact, notification/legal decision, corrective action, and follow-up owner.

For a suspected unauthorized employer submission, immediately pause all application execution, preserve the employer evidence reference and signed audit chain, and do not tell a candidate that an application was sent until receipt evidence is independently reconciled.

## Candidate data requests

- Export: the signed user can choose **Download my cloud data**. `/api/account-data` authenticates the exact subject, creates or replays one encrypted tenant-bound background task, and lets the UI poll only aggregate task state before downloading an integrity-checked encrypted private-Blob result. The export contains only that tenant's vault, campaign state, durable runs/packages, application records, and value-free browser-task metadata. Artifact binaries stay behind their authenticated download route; the export includes their integrity metadata. Export files expire after 24 hours, are removed by the worker and account deletion, and are never returned partially. Status polling has its own bounded rate-limit scope so one normal 90-second UI polling window cannot exhaust the stricter create, download, or deletion limits.
- Correction or revocation: create a new fact version or revoke the confirmed fact; never silently rewrite provenance history.
- Job Agent authorization: **Saved Info → Pause agent & revoke** writes the encrypted revocation record before shutdown. Verify queued/leased browser tasks become cancelled-before-start, active runs/checkpoints and daily scheduling pause, and resumable provider sessions receive confirmed close requests before recovery metadata is removed. An executing task must remain reconciliation-required and must never be retransmitted or reported cancelled. If provider close or another cleanup step fails, the API still reports authorization revoked, returns only content-free counts/flags, retains the encrypted recovery reference, and blocks session restore/new worker execution. Reauthorization requires all current policy versions and scopes again; it never revives a consequential approval.
- Stop cloud backup: disable future vault persistence and explain what remains on the current device.
- Deletion: the signed user chooses **Delete Job Agent cloud data**, types the exact displayed phrase, and must have signed in within 15 minutes. Before deleting other account data, the endpoint closes each remote employer-browser session through its provider and deletes only confirmed closures. If any teardown is unresolved, it returns `BROWSER_HANDOFF_CLOSE_RETRY_REQUIRED` with content-free closed/deleted/retry counts and preserves the remaining encrypted recovery references; repeat the same deletion request after provider recovery. Once preflight succeeds, the ordered deletion coordinator lists the exact tenant prefixes and Redis object indexes, deletes queued/completed account exports and provider documents before run metadata, sweeps indexed and orphaned follow-up reminders, deletes the tenant's vault, campaign state, durable runs, browser/receipt/submission tasks, application sessions and Redis audit entries, clears bounded residual idempotency keys, revokes all device sessions, clears the current cookie, and returns exact content-free counts. A provider list/delete failure stops before metadata deletion; a later retry is idempotent. Device-local browser data remains and is disclosed. Billing, subscription, fraud-prevention, and legally required transaction records are outside this operational-data control and must follow their separately disclosed retention process. External retention-locked evidence, once introduced, needs a documented legal-retention exception rather than a false deletion claim.
- Export completeness: the background task paginates every run, application, browser-session, browser-task, submission-task, and receipt-task index and records the scanned/exported/stale counts for each collection. Require `scope.operationalCollectionsComplete: true`. If active work changes an index during export, the task fails without an attachment; the same control returns to one-click retry after the run settles. A collection above 10,000 index records or a final JSON payload above 20 MiB also returns no partial attachment and requires an assisted complete export rather than silent truncation.
- Secrets: passwords, OTPs, CAPTCHA answers, identity-verification responses, and session cookies are never accepted into the vault, logs, or support tickets.

## Pilot support script

Ask only for the blocked action:

- Sign-in: "Open the employer page and sign in there. 1stStep does not receive or save your password."
- OTP/CAPTCHA: "Complete this directly on the employer page, then return and tap Continue. Do not paste the value into 1stStep."
- Ambiguous fact: show the employer question, the proposed answer, provenance, and confidence; require an edit or explicit confirmation.
- Transmission: show the exact employer, requisition, document version, field categories, and 15-minute scope before approval.
- Submission: show the final reviewed package and employer; require a separate action-time confirmation. Do not combine it with transmission approval.

If the user leaves, preserve the non-secret checkpoint and continue other eligible work. Do not repeatedly prompt or silently retry a consequential step.

## Current production boundary

The sellable beta is a supervised job-search and application-preparation agent. It can save substantial candidate time finding, filtering, ranking, and preparing truthful role-specific materials. It is not yet an unattended auto-apply service, and the product must say so plainly.
