# Durable Job Agent runtime

## Controlled-pilot admission

Legacy product tier, explicit Job Agent entitlement, and pilot admission are independent. A non-free legacy tier never grants Job Agent API access by itself. During the controlled beta, `JOB_AGENT_ACCESS_POLICY_VERSION` and `JOB_AGENT_CONTROLLED_BETA_INCLUDED_TIERS` define which verified legacy subscription restores may receive the encrypted `job-agent-controlled-beta` session grant; the policy creates no charge and enables no checkout. Existing sessions without that explicit grant fail closed and must be restored after the reviewed policy is configured. `JOB_AGENT_PILOT_ENFORCEMENT=false` prevents the launch manifest from declaring the controlled beta ready. When enforcement is enabled, `JOB_AGENT_PILOT_MAX_USERS` must be an integer from 1 through 10 and `JOB_AGENT_PILOT_ALLOWED_TENANTS` must contain no more than that many unique 40-character HMAC tenant IDs. Candidate emails are never stored in the allowlist. Both subject-facing API work and pseudonymous tenant background work pass through the same admission check before consent can authorize execution. A malformed or missing allowlist fails with `JOB_AGENT_PILOT_NOT_CONFIGURED`; a signed but non-invited tenant receives `JOB_AGENT_PILOT_INVITE_REQUIRED`. Signed users keep account export/deletion, sign-out, and authorization-revocation access even when they are removed from the pilot.

## Release boundary

The production-safe runtime performs direct-employer ATS discovery only. It does not sign in to employer accounts, control employer tabs, fill forms, transmit candidate data, or submit applications.

Signed Job Hunt Pass users start a run through `POST /api/job-agent-runs`. The request is tenant-partitioned, encrypted with AES-256-GCM, idempotent, rate limited, and immediately attempts the safe discovery step. A failed or interrupted run remains queued for retry. `PATCH /api/job-agent-runs?id=...` pauses or resumes the caller's run; another tenant receives `404` rather than existence information.

The Job Agent authentication path uses a random opaque `Secure`, `HttpOnly`, host-only cookie. Its subject and tier exist only inside an AES-256-GCM Redis record keyed by an HMAC of the random token. Sessions expire after seven days, rotate without exposing a bearer value to concierge JavaScript, allow current-device or all-device revocation, and cap each subject at 20 active sessions. `/api/user-session` is the rate-limited rotation/revocation boundary. Legacy bearer tokens remain accepted only for the wider app during migration.

## Durable execution contract

- States: Searching, Preparing, Waiting for You, Paused, Finished, Failed.
- One lease token is generated per claim and stored only as a SHA-256 hash.
- Workers heartbeat and must present the current lease to finish or retry a run.
- Transient failures retry up to four attempts with bounded exponential backoff.
- Terminal failure is explicit; it is never rendered as Submitted. A user may deliberately retry a failed run, which resets its attempt budget without changing its run identity.
- A claimed run remains in the due index at its lease-expiry time. If a worker crashes, another worker can reclaim it after the lease instead of losing the run.
- Run payloads and results expire after 30 days.
- Idempotency keys expire after 24 hours.
- The queue and tenant indexes contain opaque run and HMAC tenant identifiers only.
- Missions reject emails, phone numbers, credentials, OTPs, CAPTCHA answers, resumes, and private-profile fields.
- Public job descriptions are redacted before encrypted persistence.

`GET|POST /api/job-agent-worker` is protected by `Authorization: Bearer CRON_SECRET`. On the connected Vercel Pro project, an hourly cron invokes the worker and drains up to three due daily schedules plus one recovery run. User-started runs execute immediately; the hourly drain is recovery and background continuity, not the primary latency path. A Hobby deployment must remove or consolidate this third cron before deployment because Hobby projects permit only two cron jobs.

The protected daily health job checks variable presence and performs an expiring Redis read-after-write probe. Vercel CLI listings prove only that encrypted variable names exist; they do not prove usable runtime values.

`GET /api/job-agent-readiness` is a narrowly scoped, origin-restricted, rate-limited liveness probe. Without synthetic query flags it is read-only and reports only whether the durable store, encryption configuration, tenant partitioning, and direct-employer discovery control plane are available. It never exposes queue depth, tenant identifiers, run records, secrets, or admin evidence. Any session, notification, audit, package, or deep lifecycle flag requires the exact cron bearer plus `X-Job-Agent-Readiness-Drill: CREATE_RESTORE_DELETE_SYNTHETIC_RECORDS`; an administrator browser session cannot trigger those writes.

An explicitly requested, more tightly rate-limited `?deep=1` probe creates a random synthetic tenant, completes the encrypted create → lease → finish → restore lifecycle without any employer call, and deletes the fixture before responding.

The protected production drill requests `?session=1` together with the other synthetic lifecycle checks. It creates, restores, revokes, and confirms deletion of one synthetic opaque signed-user session. It never uses a real email account or sends a verification message. The supported operator client makes one attempt, requires the exact production endpoint and action-confirmation phrase, returns content-free evidence, and treats a timeout as outcome-unknown rather than retry-safe.

## Applicant vault

Signed Job Agent users may explicitly opt into a separate applicant vault through `/api/applicant-vault`. The vault is not campaign metadata: confirmed facts and document text are tenant-partitioned and encrypted with AES-256-GCM, writes use optimistic concurrency and idempotency, and the user can edit, revoke, export, stop backup, or delete the cloud copy. The API rejects credentials, OTPs, CAPTCHA answers, unconfirmed facts, protected-demographic values, and automatic reuse of consequential answers. Optional demographics are limited to an unanswered or prefer-not-to-answer default.

The controlled beta keeps encrypted document text in Redis with a 750 KB per-vault limit and one-year TTL. Production scale should move document bodies to tenant-scoped object storage with envelope encryption, malware scanning, retention controls, and a durable external audit sink; only encrypted metadata/version pointers should remain in Redis.

The deep readiness probe also verifies synthetic consent → fact version → encrypted persist → restore → delete for the applicant vault. It never contains real candidate data.

## Durable role packages

`/api/application-packages` creates a tenant-scoped `application_package` run only for a role restored from that same tenant's finished direct-employer discovery run. The server requires the published-feed authority marker and exact employer, title, requisition, and HTTPS Apply URL match, then rebuilds the job text and Apply identity from the encrypted discovery result; a browser-supplied `applyPathActive` claim or edited job description cannot satisfy this gate. The candidate-reviewed master resume remains an explicit private input. Input and generated output use the same AES-256-GCM run envelope, idempotent creation, lease/heartbeat recovery, bounded retries, tenant isolation, and 30-day retention as discovery runs. Passwords, OTPs, CAPTCHA answers, access tokens, and credential fields are rejected even inside encrypted payloads.

Each new generation consumes three package budget units. The controlled beta defaults to ten package generations per signed account per day and 100 globally; `PACKAGE_GLOBAL_DAILY_UNITS` can lower or raise the global allowance after measured cost review. Reads and retry-status checks use a separate higher allowance.

Generation returns a versioned private draft plus hashes and a source map. Deterministic checks route the package to `Waiting for You` when they find unsupported numbers, altered contact values, protected-trait content, credentials, irrelevant AI language, markdown/table risks, first-person resume language, or source excerpts not present in the reviewed master.

A passing truth check now produces restrained, single-column DOCX and PDF resume artifacts and, when requested, DOCX and PDF cover-letter artifacts. The generator uses real Word numbering rather than typed bullet characters, no tables, columns, images, or decorative templates. It accepts a verified one- or two-page resume based on supported source substance and never pads a short history merely to force a second page. The worker extracts DOCX and PDF text, checks source order, verifies PDF page counts, records byte counts and SHA-256 hashes, encrypts the artifacts inside the tenant run, and returns only metadata through the package API. Signed tenant-scoped downloads are served through `/api/application-package-artifact` with an integrity recheck and `private, no-store` caching.

Candidate edits are immutable revisions rather than browser-only overwrites. `POST /api/application-packages` with `action=revise` restores the exact tenant-owned base run, carries forward its reviewed master resume, verified job text, and source map, then creates a new encrypted run and document version. The revision path does not call an AI provider. It repeats truth/source-map checks, ATS checks, DOCX/PDF generation, extraction, pagination, and integrity hashing; it clears prior render/approval evidence and must pass a new isolated render before it can return to Package Ready. The idempotency key is stable for the base version and edited content, so a slow retry does not create duplicate revisions.

The resulting state is `ats-artifacts-verified-awaiting-isolated-render`. It still cannot become Package Ready until an isolated render worker has produced and inspected every page for clipping, overlap, missing glyphs, and spacing defects. The prior admin self-attestation button was removed; there is no client path that can fabricate render evidence. Local template QA uses the bundled renderer when LibreOffice is available, with installed Word as a development fallback. Production must use an isolated, patched document-rendering worker with no outbound network, ephemeral storage, resource limits, malware scanning, and automatic teardown.

`/api/application-package-render` is the signed, tenant-scoped activation boundary for that production stage. It is fail-closed unless both `DOCUMENT_RENDER_SANDBOX_ENABLED=true` and a reviewed `DOCUMENT_RENDER_SANDBOX_SNAPSHOT_ID` are configured. The snapshot contract requires patched LibreOffice, Poppler, Python, and Pillow. Each invocation boots an ephemeral Firecracker microVM from the snapshot with `networkPolicy: deny-all`; writes only integrity-checked package artifacts with restrictive file modes; converts DOCX files, rasterizes every DOCX/PDF page, checks blank pages, page count, edge clipping, page density, dimensions, and extracted text; returns only bounded metrics and hashes; and always destroys the VM. No applicant credentials, tenant keys, provider keys, or employer sessions enter the sandbox.

The render API has separate per-account and global daily limits. Enabling Vercel Sandbox can create usage charges, so the checked-in default is disabled and no sandbox or paid render run is created by deployment. After an authorized snapshot/cost review, configure `DOCUMENT_RENDER_ACCOUNT_DAILY_UNITS` and `DOCUMENT_RENDER_GLOBAL_DAILY_UNITS`, activate the two render variables, run the deep readiness probe, and verify one synthetic package before allowing controlled-beta documents through the gate. A successful signed render report is encrypted back into the existing durable package version and is the only application path that advances it to Package Ready.

The deep readiness probe verifies synthetic encrypted package create → lease → finish → restore → delete without calling an AI provider or employer.

## Durable application sessions

`/api/application-sessions` provides the signed, tenant-isolated control record for future employer-browser work. A session cannot be created from client claims alone: the API restores the tenant's exact encrypted package run and requires a Finished package with matching isolated-render evidence, zero unresolved QA issues, and the same document version. This keeps unrendered, edited, mismatched, or fabricated packages out of the application pipeline.

`/api/employer-browser-session` adds the resumable handoff metadata boundary. It accepts only an authenticated tenant-owned application-session ID, stores the provider reference and exact employer page in an AES-256-GCM envelope, limits metadata to 24 hours, applies account/IP/global rate limits, and never returns the provider reference to the browser. Signed-user export and deletion include the redacted session summary and remove its tenant index. Deleting an application session closes and deletes its associated browser-session record first.

The checked-in `synthetic-fixture` provider is development-only, read-only, limited to `.example.test`, and performs no navigation or provider call. Its SVG preview contains employer host and field labels only—no candidate values, credentials, cookies, OTPs, CAPTCHA answers, or page capture. Production rejects that fixture.

`remote-stream` now implements a vendor-neutral HTTPS provider contract but remains explicitly disabled by default. Activation requires a public HTTPS API and exact stream origin, a server-only provider key, separate provider-cost approval/version, and separate CSP-origin approval/version. Create requests contain only the verified target URL, exact one-host network allowlist, bounded lifetime, opaque idempotency key, and policies requiring submission blocking, provider-only credential handling, no recording, no returned candidate values, and blocked downloads. The provider must attest those policies and return a value-free field schema whose SHA-256 is independently recomputed. Stream URLs must use the exact configured origin; the client repeats that origin check and renders the session in a sandbox without popup or top-navigation permissions. Ambiguous create failures use the same provider idempotency key for lookup, resume requires the exact employer URL/schema, and deletion removes encrypted recovery metadata only after `closed` or `missing` is confirmed. Teardown remains available with valid transport credentials even after new-session activation is disabled.

The production CSP still excludes every unselected stream provider origin. Choosing and authorizing a provider requires an explicit CSP change and verified recovery drill; setting approval variables without the corresponding reviewed header change is invalid operational practice. The launch manifest distinguishes `EMPLOYER_BROWSER_REMOTE_STREAM_NOT_READY` from `EMPLOYER_BROWSER_SESSION_RECOVERY_NOT_VERIFIED`; configured transport alone is insufficient. Recovery evidence must be a recent signed envelope over a retained artifact hash, carry a safe evidence ID, and remain bound to the active provider endpoints and approval versions.

Every saved browser handoff is also placed in a global content-free expiration index containing only its opaque session ID and due time. The background worker claims expired sessions with a short single-worker lease, requests provider teardown, and deletes tenant mapping plus encrypted provider reference only after the provider confirms `closed` or `missing`. Provider outages and ambiguous responses retain the encrypted record and requeue it with bounded exponential backoff; a worker crash becomes eligible after lease expiry. Cleanup remains callable when creation is disabled, provided teardown transport credentials still exist. Operational metrics expose only completed/retry/failure counts, never provider references, employer URLs, candidate identity, or field data.

Ending, replacing, deleting an application, or deleting the tenant account requires provider-confirmed teardown before an encrypted recovery reference is deleted. All callers share the same lifecycle coordinator. If teardown fails, the API returns `BROWSER_HANDOFF_CLOSE_RETRY_REQUIRED` and preserves that reference for a later retry. Expired sessions use the same close-before-delete path. Tenant-wide deletion closes every available session, deletes confirmed closures, preserves unresolved references, and returns content-free partial-progress counts before any non-browser account data is removed. This prevents a transient provider failure from creating an unreachable live session or a misleading complete-deletion claim.

`/api/application-receipts` is a browser-inaccessible, service-to-service evidence endpoint for the isolated receipt worker. It rejects browser origins and requires an HMAC signature over the canonical request body, a timestamp no more than five minutes old, and a single-use nonce retained for ten minutes. The signing key is `JOB_AGENT_RECEIPT_SECRET`; it must never be shipped to the frontend or browser worker page context. The worker uses a pseudonymous tenant ID, not the candidate email, and cannot create or approve the user-facing final-submission action.

The endpoint supports three exact workflow records: approved personal-data transmission, submission-attempt evidence, and authoritative employer-receipt verification. Final-review readiness is instead a signed-user `/api/application-sessions` action named `request-final-review`. It accepts only the session version and an explicit value-free confirmation that the exact preserved employer form was reviewed; field schema, document version, approved scope, and filled field keys are restored and cross-checked on the server. The receipt action accepts signed raw evidence only as `verify-authoritative-receipt`; callers cannot provide a precomputed receipt summary or directly mark a session Submitted. Confirmation pages must remain on the exact verified employer host, contain a positive receipt signal, and match the recorded response fingerprint. Email evidence must pass DKIM and DMARC, come from an independently configured sender-domain allowlist, and identify the exact requisition or employer/title. ATS API evidence must come from an independently configured provider allowlist, have a connector-verified signature, and match the exact requisition and document version. A submission attempt alone never changes the tracker to Submitted.

After a completed or user-reconciled fill, the workspace shows **Review final application**. That review creates a distinct `SUBMISSION_APPROVAL` action only when the encrypted checkpoint, transmission attempt, approved field scope, and exact package version all match. **Approve final submission** then records a 15-minute, single-use permission. When every independent production gate is eligible, the signed-user route atomically reserves that exact scope for the durable submission worker; all supplied defaults keep it disabled. The worker consumes approval before the isolated provider instruction begins. Nothing becomes Submitted until an authoritative employer receipt is verified.

If that final permission expires before execution begins, the saved application returns to **Needs You** with **Renew final approval**. Renewal accepts no browser-supplied scope, schema, document, or field data: the server restores the encrypted checkpoint and transmission attempt, recomputes the exact approval scope, verifies that no submission attempt exists, supersedes the expired permission, and creates a new action-time approval. It never retries or submits automatically.

`lib/application-receipt-capture-provider.js` implements the disabled-by-default transport into that verifier. Activation requires an independently approved version, the exact public HTTPS application host and exact `/api/application-receipts` path, the internal signing key, and an explicit subset of `page`, `email`, or `api` authority kinds. Email and API kinds additionally require their authority allowlists. The connector signs the exact body, forbids credential/challenge fields or values, sends one request with redirects disabled, and returns only a content-free outcome. It never returns raw evidence. A conflict becomes `reconciliation-required`; a timeout or 5xx becomes `unknown`. Only the separate durable receipt workflow may schedule another read-only evidence check after reconciling persisted state; it never repeats the submission action. No outcome other than a verifier-confirmed response can become Submitted.

Only the verifier's SHA-256 evidence hash, masked confirmation reference, verified employer origin, timestamps, source, and method enter durable storage. Raw email/page/API content is kept in call scope and is neither stored nor logged; candidate-specific confirmation paths, query strings, and fragments are discarded. Replayed signatures and optimistic-version conflicts fail closed. The connector is implemented but remains disabled and unapproved in the supplied environment until a real isolated employer session or approved mailbox/API is provisioned and independently exercised. The launch manifest reports capture readiness separately from receipt-ingestion signing and requires it before final execution can become eligible.

`lib/application-submission-provider.js` defines the separately approved, disabled-by-default final-action protocol for the existing stateful remote browser session. It accepts only an already-started exact-scope durable reservation whose single-use approval has been consumed. Its one provider request contains an opaque idempotency key, exact employer host/page, schema hash, document version, requisition, scope hash, and policies requiring one attempt, no returned candidate values, and no raw receipt evidence. It never performs a lookup or retry after an ambiguous call. Timeout, transport error, invalid response, or forbidden returned data becomes `SUBMISSION_PROVIDER_OUTCOME_UNKNOWN`, remains uncounted, and creates a **Needs You** state that explicitly says not to resubmit.

`lib/application-submission-task-store.js` and `lib/application-submission-task-worker.js` provide the tenant-isolated encrypted orchestration boundary around that protocol. Final approval and the opaque exact-scope task are committed atomically. A queued or expired lease may recover only before provider start; approval is consumed and durably persisted before the task enters `executing`. A crash after that transition becomes outcome unknown and is never re-leased. The worker rechecks current consent before restoring the session, before consuming approval, and once more immediately before the provider boundary. It restores the encrypted remote-browser reference only inside the worker and records either minimized attempt evidence, a verified pre-provider cancellation, or a non-retryable unknown result. Authorization revocation cancels queued and armed-before-provider work, while an executing provider task remains for reconciliation. Account export/deletion includes redacted task metadata. All durable-execution controls default off. The launch manifest and worker both require a signed, 30-day `JOB_AGENT_FINAL_SUBMISSION_EXECUTION_EVIDENCE` envelope bound to the exact provider endpoints, receipt policy, and approval versions. Without it, `FINAL_SUBMISSION_SUPERVISED_EXECUTION_NOT_VERIFIED` keeps `submissionsEnabled` false.

`lib/application-receipt-task-store.js` and `lib/application-receipt-task-worker.js` complete the authoritative-receipt handoff. A successful provider attempt and its encrypted, exact-scope receipt task are committed atomically. The task stores no page text, candidate values, credentials, or confirmation evidence. It restores only the matching tenant session and browser handoff, performs bounded read-only employer-page checks for up to 24 hours, and passes raw evidence directly in memory to the signed verifier. Invalid or secret-bearing provider responses are terminal. Transient absence may be rescheduled; submission is never repeated. Exhaustion, lost browser state, or unverifiable evidence creates one **Verify employer receipt** Needs You item and keeps the application uncounted. Consent revocation cancels pending checks, account export includes redacted metadata, deletion removes terminal metadata, and encryption-key maintenance covers this record type. The worker is independently disabled until `JOB_AGENT_RECEIPT_VERIFICATION_WORKER_ENABLED`, `JOB_AGENT_RECEIPT_VERIFICATION_WORKER_APPROVED`, and a valid `JOB_AGENT_RECEIPT_VERIFICATION_WORKER_APPROVAL_VERSION` are configured with the browser and receipt-capture gates.

Every durable application-session create or update atomically appends an encrypted audit ledger entry in the same Redis script. Each entry commits the complete encrypted-session version through a SHA-256 digest, points to the previous entry, and is HMAC-signed with the separate `JOB_AGENT_AUDIT_SECRET`. Reads verify the encryption envelope, session/sequence identity, hash chain, signature, entry count, and current audit head before returning any administrative evidence. The subscriber session response exposes only the ledger count and signed head; `/api/application-audit` returns the redacted verified ledger only to a server-confirmed `OWNER_ACCESS_EMAILS` administrator.

Application sessions and audit entries retain for 365 days and allow at most 500 signed mutations per session. Reaching the cap fails closed until the ledger is archived. The existing explicit candidate deletion path removes the session and its ledger entries; ordinary updates cannot alter or remove earlier ledger entries. This Redis implementation is tamper-evident and append-only during retention, but it is not a regulatory WORM archive. Before a larger launch, stream signed heads to retention-locked object storage or an external audit sink with backups, regional recovery, legal-hold policy, and tested restore procedures.

An administrator may `POST /api/application-audit` with `{ "subject": "...", "id": "...", "head": true, "download": true }` to produce a separately HMAC-signed, content-free audit-head bundle. POST is required so tenant identity does not enter a request URL. The bundle contains only an opaque record reference, entry count, verified ledger head/signature, retention policy, export time, digest, and export signature; it excludes the session identifier, timeline entries, and candidate field values. `JOB_AGENT_AUDIT_EXPORT_SECRET` must be distinct from the ledger and data-encryption keys. Verify a downloaded bundle offline with `npm run security:verify-audit-head -- <file.json>` in a protected environment containing that secret. This proves bundle authenticity and tamper detection; it does not prove that an archive is retention locked, replicated, or recoverable.

The encrypted session stores employer/requisition identity, the verified package version, masked field previews and answer-vault references, approval scopes, non-secret form-structure checkpoints, one consolidated action list, and a bounded timeline. It explicitly rejects password, passcode, OTP, CAPTCHA, MFA, verification-code, cookie, token, credential, and secret fields at every nesting level. Form checkpoints contain only a schema hash, staged field keys, page URL, step key, and attached document version—never field values or browser authentication material.

Transmission and submission approvals are separate, exact-version, exact-employer, action-time grants with 15-minute expirations and an unused/consumed distinction. Confirming either grant records permission only unless every final-execution launch gate is eligible, in which case final approval atomically queues one exact single-attempt task. The gated no-submit path exact-inspects the employer form in an isolated microVM, atomically reserves its schema and fact references in an encrypted tenant-opaque task, consumes the one-time sharing grant before values enter the worker, and fills only reserved ordinary fields. Values use mode-0600 ephemeral files, never command arguments, logs, queue state, or result payloads. A task may be re-leased only before execution starts; after start, a timeout or crash becomes outcome unknown and automatic retransmission is prohibited. Reconciliation derives completion only from an already-persisted exact-scope checkpoint or moves the application to Needs You. There is no public API for fabricating an employer receipt or marking a session submitted. Search, package, and browser-task records retain for 30 days; final-submission task metadata retains for the documented account/audit lifecycle and never contains candidate values.

The optional production archive boundary is `lib/application-audit-archive-provider.js`. It is disabled by default and accepts only a valid signed, content-free audit-head export. Activation requires an exact allowlisted HTTPS endpoint, explicit approval and contract versions, a reviewed legal-hold policy version, 365-3650 retained days, a bearer credential, and a separate acknowledgement HMAC secret. Requests use the audit digest as an idempotency key and prohibit query credentials and redirects. A 2xx response is insufficient: the provider must return the exact stored digest, immutable object version, exact retention deadline, fixed content-free flags, and a valid acknowledgement signature. Any mismatch fails closed with `retentionLockVerified: false`. This adapter does not itself prove replication, restore, or provider enforcement; recent independently retained, scope-bound launch evidence remains mandatory.

## Daily background search

`lib/job-agent-schedule-store.js` stores one encrypted daily discovery mission per tenant. The global due index contains only an HMAC-derived tenant ID; it contains no email, resume, contact information, or mission text. Cron claims use short leases and automatically become eligible again after a worker crash. Each due schedule rechecks the current consent policy before enqueue, uses a tenant-and-date idempotency key, and advances only after the durable run exists. Consent revocation first persists the revoked authorization, then cancels queued or leased browser work, closes resumable provider sessions, pauses active runs and application checkpoints, and removes the schedule from the due index. Workers recheck consent after claiming and again immediately before consuming the one-use transmission approval.

`JOB_AGENT_SCHEDULE_ENABLED` defaults off. Activation also requires a positive `JOB_AGENT_SCHEDULE_GLOBAL_DAILY_RUNS` cap; invalid or missing caps fail closed in configuration, readiness, and the production security gate. The global UTC-day counter defers excess schedules rather than dropping or padding work. The existing signed-user data export and deletion paths include the schedule. Scheduling invokes only direct-employer discovery and can never create an application session, transmit data, or submit an application.

After a successful discovery run and a final consent recheck, the same leased worker performs a bounded freshness sweep over up to ten older active Greenhouse, Lever, Ashby, or SmartRecruiters cards in that tenant's encrypted campaign state. It re-fetches the exact requisition from the configured employer catalog. A missing/closed role or a material title, Apply URL, compensation, or employment-type change retires the card as `Rejected/Closed`; a transient provider failure leaves that card unchanged and the sweep continues. The worker never reads candidate vault values, never changes submitted/receipt/interview history, and saves through compare-and-set so a concurrent browser update wins. Operational evidence is fixed, content-free counts only.

### Background-worker monitoring

Every authorized worker invocation writes an opaque, content-free heartbeat with only a timestamp and `started`, `succeeded`, or `failed`. The admin-only operations response classifies it as `running`, `healthy`, `incomplete`, `failed`, `stale`, or `unknown`; a `started` heartbeat older than ten minutes is incomplete, and any heartbeat older than 150 minutes is stale for the hourly cron. Production readiness fails closed at `background-worker-heartbeat` unless the configured scheduler is `healthy` or currently `running`. Daily allowlisted counters distinguish invocation, enqueue, idempotent replay, consent pause, budget deferral, scheduler failure, submission attempt/expiry/unknown/failure, receipt pending/verified/review/failure, Stripe webhook completion/duplicate/deferred-retry/failure, and operator-alert acceptance/retry/dead-letter health. Candidate identity, mission text, job text, URLs, requisitions, Stripe event IDs, and exception details are prohibited from these metrics. Consequential submission uncertainty, receipt-worker failures, and Stripe webhook processing failures additionally enqueue deduplicated content-free operator alerts; ordinary pending checks, expected concurrent webhook deferral, and candidate-facing receipt review do not page an operator. Every alert carries the configured receiver contract version and a deterministic fingerprint of its fixed schema/event set. The heartbeat worker leases queued alerts, retries transient delivery up to four attempts with one stable record-derived idempotency key, and leaves terminal failures in an aggregate dead-letter queue. Delivery or observation failure is logged and counted locally without recursively using the failed alert channel. Deduplication is contract-specific, and signed launch evidence is invalidated by any endpoint, contract-version, supported-event, or delivery-contract change. Worker failure returns HTTP 500 to make Vercel Cron surface the failed invocation while preserving the leased work for recovery.

The same admin-only response reports aggregate consequential-queue health directly from Redis sorted-set cardinality and due-time scores. Submission health separates queued/leased work from reconciliation work because the reconciliation index intentionally retains both timed-out executions and already-unknown outcomes until acknowledgment. Receipt health reports pending checks and checks more than two hours past their scheduled retry. The response never reads or decrypts task payloads and never exposes task, tenant, application, employer, or requisition identifiers. `attention-required` therefore means overdue queue work or due reconciliation exists; it is not a submission or receipt claim. Every heartbeat also performs this observation: attention sends one cooldown-deduplicated generic warning, while an observation failure records a critical generic alert, marks the heartbeat failed, returns HTTP 500, and exposes only `unknown` queue state so the scheduler cannot silently report success.

All paid Job Agent boundaries share a second, atomic USD-cent ledger in Redis. It reserves an operator-approved worst-case amount before generic AI, package AI, document rendering, remote browser-session creation, Needs You email, or private artifact persistence can contact a provider. Global and category caps are checked in one Lua operation using only an HMAC operation ID. Unknown provider outcomes settle at the maximum; only a path proven not to have contacted a provider releases capacity. ### Needs You notifications

Email reminders are optional and off by default for every user. Only a newly created open application action may enqueue a notification. The outbox encrypts the authenticated recipient/action identity and places only a pseudonymous record key in the due index. User-scheduled post-submission follow-ups use the same outbox. ### Encryption-key rotation

All encrypted Job Agent records now use one shared bounded AES-256-GCM keyring. New envelopes include the non-secret active `keyId`; legacy envelopes without a key ID remain readable by attempting the active key and then at most three explicitly configured prior keys. Tenant/record AAD is unchanged, so ciphertext cannot be moved between users, records, sessions, or audit entries. Production fails closed without an explicit `BETA_DATA_ENCRYPTION_KEY_ID`. `BETA_DATA_DECRYPTION_KEYS` is an optional server-only JSON object mapping prior safe IDs to their 32-byte keys; the total active-plus-prior ring is capped at four.

Use `npm run security:key-rotation-drill` after staging the three encryption variables. The drill is local and non-destructive: it encrypts only a synthetic marker with the active key and proves every configured prior key can still be recovered through the full ring. It prints IDs and counts only, never key material. A normal record update re-encrypts the changed envelope with the active key. Immutable historical audit entries and unmodified records retain their original encryption, so a prior key must remain available until every dependent record has expired or a separately verified bulk re-encryption has completed. Removing a prior key early strands data; rotating a compromised key does not retroactively restore confidentiality and requires incident handling.

`npm run security:reencrypt-records` is the dry-run-only default for retiring a prior key. It scans only the exact allowlisted Job Agent record shapes, including encrypted employer-browser handoff and final-submission task metadata, decrypt-verifies every recognized envelope in memory, and returns content-free totals plus a resumable pattern/cursor checkpoint. It never prints keys, Redis record IDs, candidate values, plaintext, ciphertext, IVs, or tags. Use `--max-records=N` to bound a pass and resume with the returned `--pattern-index` and `--cursor`. Apply mode additionally requires both `--apply` and `REKEY_CONFIRMATION=REENCRYPT_JOB_AGENT_RECORDS`; each rewrite compares the current record version atomically and preserves its remaining Redis TTL. Conflicts are not overwritten and produce a non-zero exit for a later retry. Run a complete dry pass, establish an approved backup/change window, pause affected writers when practical, and obtain explicit operator authorization before apply mode.

`npm run security:recovery-drill` requires `RECOVERY_DRILL_CONFIRMATION=CREATE_AND_DELETE_SYNTHETIC_RECORD`. It creates one 120-second synthetic encrypted Redis record, captures its exact encrypted representation in memory, deletes it, restores it, verifies ciphertext integrity and post-restore decryption, and deletes it in `finally`. This proves the application-level recovery mechanics and key availability, not provider backup retention or disaster-recovery guarantees. Managed Upstash backup/PITR availability, retention, region, access controls, and a restore into an isolated recovery database remain an external production gate until independently verified.

`npm run security:object-storage-drill` requires `OBJECT_STORAGE_DRILL_CONFIRMATION=CREATE_SCAN_READ_DELETE_SYNTHETIC_OBJECT` and the exact production configuration. It creates one generated value-free PDF under an opaque tenant/run namespace, sends it through the configured exact-host malware scanner, encrypts and writes it with the ordinary private-object path, reads and integrity-checks it, deletes it, verifies absence, and attempts cleanup again after any post-write failure. The command emits only content-free booleans and a count. Retain the result, independently review it, and sign it as `private-object-storage`; the signed evidence expires after 90 days and is invalidated by a storage mode, scanner endpoint/host, environment, or encryption-key ID change. The drill can incur configured scanner, storage, and Redis usage, so do not run it without explicit authorization and approved monetary caps.

The ordinary subscriber surface now restores those sessions across sign-ins, merges all open actions into the single **Needs You** queue, and presents one simple job card per role. A Package Ready card can create an idempotent session. The action panel shows only masked field previews, the exact employer and package version, the verified employer domain, and explicit sharing or final-submission controls. Login, OTP, CAPTCHA, identity, ambiguous-fact, nonstandard-certification, and outside-employment-conflict steps direct the user to the verified employer page and accept only a value-free completion confirmation. The Job Agent API rejects extra answer fields plus password and challenge-value keys; no answer, credential, identity document, certification value, or conflict response enters the session. An outcome-unknown employer fill is not dismissible or automatically retried: the user must review the exact preserved form and confirm either that the approved fields are present or that nothing was filled. An outcome-unknown final action exposes no retry or approval button, keeps the employer page available for inspection, and remains uncounted pending authoritative receipt verification.
