## Product boundary for this slice

This wave turns the concierge into a reusable local orchestration and evidence model. It does not claim autonomous discovery, overnight background execution, employer-form submission, receipt capture, or encrypted multi-user cloud storage. Those remain separate deployment and architecture gates.

## Application Readiness Interview and autonomy

| Capability | Local implementation | Safety boundary / remaining production work |
|---|---|---|
| One-time readiness interview | Covers 24 recurring answer groups. The primary path is now one click: build a proposal from the locally saved profile, master resume sections, and confirmed truth profile; review the proposals once; then confirm them together for matching reuse. Remaining questions and manual corrections are collapsed secondary controls. | The browser-local store is not the consented encrypted multi-user vault. Cloud persistence needs tenant isolation, application encryption, KMS-backed key management, export/deletion APIs, and retention controls. Resume section parsing is deliberately conservative; ambiguous or absent sections remain unresolved instead of being inferred. |
| Reusable facts | Each answer records normalized field, value, verification state, source, sensitivity, scope, created/updated timestamps, optional expiry, and automatic-reuse permission. Saving requires explicit confirmation; free text is not learned silently. | Document verification, version conflict UI, scoped tenant authorization, and cross-device synchronization remain missing. |
| Standing authorizations | One click confirms conservative, mission-scoped defaults for transmitting approved facts, credential-flow account creation, ordinary privacy terms, matching routine screening answers, and leaving optional demographics unanswered. Individual policy customization is secondary. | Plaintext passwords, OTPs, CAPTCHA answers, identity checks, material consents, signatures, conflicts, and unusual screening remain human-controlled exceptions. |
| Semantic and confidence gate | Exact normalized field keys or narrow aliases must meet a 0.92 confidence threshold. Ambiguity asks once; employer certification, signatures, unusual screening, conflicts, and material consents become targeted exceptions. | Production needs evaluated semantic models, versioned question taxonomy, false-match monitoring, and an ATS fixture matrix. |
| Autonomy levels | Prepare only, Auto-fill then review, and Auto-submit within standing authorization. New state defaults to Auto-fill then review. Auto-submit eligibility requires complete readiness, at least one successful audited baseline, a fully verified role, and only safe-fact/standing-policy field decisions. | Product test submission remains disabled. Enabling execution requires a hardened browser runner, action-time checks, idempotency, and receipt reconciliation. |
| Audit/export/delete | Field-answer audits retain exact question wording, fact/policy ID, confidence, and document version. Readiness data can be exported; individual facts can be deleted with a deletion audit event. | True immutability and durable deletion guarantees require server-side append-only storage and cryptographic audit controls. |

## Sales-ready simulation

The Sales demo tab is isolated from the real desk pipeline. It uses the synthetic candidate “Jordan Example,” `.example.test` employer/ATS fixtures, and a separate simulated trace. It demonstrates readiness, mission creation, discovery, requisition-based deduplication, document QA, automatic fact/policy reuse, a targeted electronic-certification exception, a simulated receipt, and interview follow-up. Every step explains why it was automatic or human-required. The simulated receipt records `transmission: none`, and demo roles never increment real `Submitted` counts.

## Contextual managed-browser vertical slice

The local-only expansion adds a contextual Application workspace overlay to `/concierge`. It appears only after a synthetic application session starts or when a saved session is resumed; chat and one-question readiness popups remain the primary experience. The workspace shows a redacted employer-page fixture, the current application step, agent status, reusable-answer provenance, staged document version, blockers, recovery controls, a redacted activity timeline, and a clearly simulated receipt.

The durable local state machine covers Discover & Verify → Deduplicate → Tailor Package → Create or Reuse Account/Profile → Autofill → Review Exception → Transmit → Submit → Verify Receipt. It pauses at an employer-specific exception, supports browser-timeout recovery, and never increments the real Submitted count from a simulated receipt. The production path still requires an isolated remote-browser service, authenticated session handoff, action-time credential-transmission confirmation, ATS adapters, encrypted tenant storage, and authoritative receipt capture.

Redacted acceptance replay fixtures encode the observed evidence rules:

- Employer candidate-portal history overrides a local-only tracker for Duplicate/In Process decisions.
- An exact direct-employer page overrides stale search snippets and aggregator location descriptions.
- City-scoped “remote” language remains Location Unverified until saved-state eligibility is explicit.
- SuccessFactors sign-in becomes Login Required, followed by action-time Transmission Confirmation Required.
- Invalid employer/title/school identifiers become ATS Configuration Blocked with resumable state.
- Activity status vocabulary includes Verified, Closed by direct page, Location Unverified, Duplicate/In Process, Login Required, Transmission Confirmation Required, ATS Configuration Blocked, and Submitted with authoritative receipt.

Additional replay fixtures cover Jabil `J2457212` and Pratt & Whitney's redacted NPI Buyer as Closed by direct page when Workday no longer exposes the requisitions; Holley Performance Brands `1552` as `Verified - Package Preparation` after direct ADP validation; and Modine `9112` as `Login Required / Retry` while retaining its ATS Configuration Blocked history. Holley's rubber/plastics preference is recorded as a `preferred gap`, while mandatory qualifications use a separate `required gap` field. ADP Continue is modeled as Transmission Confirmation Required because it sends first name, last name, email, mobile number, and phone country to the external ATS.

Batch 32 acceptance behavior adds application-scoped pauses. Modine `9112` becomes `Human Action Required - password/reset` after one explicitly authorized credential attempt returns an invalid-credential response; the form is preserved, further attempts stop, and no reset is triggered silently. After a separately authorized Password Help request transmits the saved email once, the state becomes `Password Reset Requested - Outcome Pending`. The neutral employer response is not evidence that an account exists, a matching account was found, or an email was delivered. Holley `1552` becomes `Human Action Required - OTP` after the candidate selects masked email delivery, ADP confirms a verification code was sent, and the `Enter the Verification Code` dialog remains open. The raw password and OTP never enter state, logs, or public activity. Both pipeline roles remain Package Ready, neither becomes Submitted, and another application session can continue while one is suspended. Named batch authorization records that verified profile fields and an approved resume version may be transmitted, but explicitly excludes identity verification, invalid credentials, OTPs, CAPTCHAs, and new employer-specific consent.

All candidate values in visible workspace fixtures and timeline events are masked. Passwords, OTPs, CAPTCHA responses, tokens, and receipt identifiers are never accepted or retained by the simulated session.
