# Application Concierge security boundary

## Release position

This checkout is hardened for local and preview testing, but it is **not approved for an unrestricted production launch**. No implementation can guarantee safety against everything. Production must remain fail-closed until the configuration and infrastructure gates below are independently verified.

Web API routes are necessarily discoverable on a web application. The security requirement is that discovering a route does not reveal a provider secret or authorize a privileged operation.

## Route classification

| Route | Exposure | Required protection |
| --- | --- | --- |
| `/api/ai`, `/api/concierge-discovery` | Guided preview API | Exact origin, signed user or hashed-IP guest identity, stricter guest limits, payload cap, shared production budgets, provider timeout |
| `/api/claude`, `/api/jobs` | Authenticated legacy application API | Exact origin, signed short-lived access token, payload cap, server-side usage limits, provider timeout |
| `/api/track-event`, `/api/ghl-stage`, `/api/notify-signup` | Authenticated CRM mutation | Signed access token whose subject must equal the target email |
| `/api/stripe-webhook` | Public webhook receiver | Stripe signature and configured webhook secret |
| `/api/job-agent-email-events` | Public provider webhook receiver | Raw-body Svix/Resend signature and timestamp, fixed product/sender/tenant correlation, replay protection; recipient-free encrypted suppression only |
| `/api/tally-webhook` | Public webhook receiver | Tally signature; unsigned production operation is forbidden |
| `/api/beta` | Public session issuer | Exact origin, invite code, rate limit, strong `TIER_SECRET`; fails closed when production configuration is missing |
| `/api/subscription` | Public verification/OAuth route | Email challenge, short-lived signed entitlement, OAuth state, rate limit |
| `/api/health`, `/api/beta-expiry-check` | Private operations | Bearer secret; URL query secrets are disabled in production and a missing cron secret fails closed |
| `/api/job-agent-worker` | Private operations | Hourly Vercel Cron with constant-time `Authorization: Bearer CRON_SECRET`; content-free results only; submissions always disabled |
| Job Agent subscriber data routes | Signed beta API | Revocable opaque HttpOnly session only; legacy bearer credentials receive `SESSION_UPGRADE_REQUIRED` |
| `/api/app-config` | Public non-sensitive configuration | Returns flags only; no analytics or provider token is exposed |

## Implemented controls

- Exact production and current-deployment origins replace wildcard `*.vercel.app` trust.
- Browser extensions require exact IDs from `ALLOWED_EXTENSION_IDS`.
- AI, job-search, discovery, analytics, and CRM mutation routes require a signed, expiring entitlement. Exact localhost origins may use a development-only bypass only when both `VERCEL_ENV` and `NODE_ENV` are non-production; preview and production deployments never receive that bypass.
- Provider credentials are server-only. Legacy direct Anthropic and RapidAPI browser calls were removed, and previously stored browser model keys are deleted on startup.
- Request methods, JSON content type, body length, token count, models, call types, job query parameters, ATS providers, board identifiers, and outbound hosts are allowlisted or bounded.
- Public ATS fetches are limited to the reviewed Greenhouse, Lever, Ashby, and SmartRecruiters catalog with strict board-slug validation, source caps, description caps, HTTPS-only URLs, timeouts, and bounded upstream concurrency. Greenhouse's standard host and each reviewed custom career host are allowlisted exactly per employer; Lever requisitions must resolve through the configured global or EU instance; Ashby results must use public API version 1 and remain listed; SmartRecruiters list and detail requests remain on its exact API host and Apply URLs must match the configured employer and requisition on an approved SmartRecruiters host. Every Greenhouse, Lever, and SmartRecruiters candidate is re-fetched by exact requisition before persistence. Ashby candidates must remain members of the current published board response. Path or query identity must match the requisition, URLs with credentials or nonstandard ports are rejected, and user-supplied arbitrary URLs are never fetched.
- Apply-path verification evidence is stored with the discovery result and expires after 24 hours, but package creation now re-fetches the exact allowlisted employer requisition on every request even when the prior evidence is newer. An unchanged role receives a fresh timestamp; a 404/410 or missing Ashby listing becomes Rejected/Closed without generating documents; any title, URL, description, location, work mode, employment type, or compensation change retires the old snapshot so its prior fit score and résumé cannot be reused. Package generation restores the tenant-owned finished discovery run and rejects missing, future-dated, caller-edited, changed, closed, or temporarily unverifiable employer evidence. Public opening totals come from the complete accepted feed before the bounded verification/fit sample; the UI must label both values and must never present catalog coverage as the whole market.
- Each successful durable discovery run also checks a bounded set of older active cards through the same exact, allowlisted employer sources. The sweep resolves only by opaque tenant partition, reads no applicant vault values, retires closed or materially changed roles before packaging, preserves submitted and receipt history, isolates source failures per card, and uses compare-and-set so it cannot overwrite a newer signed-user update. Its operational metrics contain counts only.
- AI system instructions are server-controlled for the concierge, resume builder, profile extractor, tailoring, cover letters, LinkedIn, and autofill. Model input and output containing apparent passwords, OTPs, CAPTCHA answers, API keys, or access tokens is rejected.
- Profile extraction output is schema-validated and size-bounded. All model text is treated as untrusted output and escaped before chat rendering.
- The model has no direct submission, credential, browser, database, messaging, or payment tool. Model output alone cannot mark an application Submitted.
- Extension autofill sends a structured context rather than a browser-authored model prompt. The server removes protected/consequential profile keys and unsafe form fields before the provider call, accepts only exact schema keys, and deterministically drops every returned value that is not present in candidate-provided profile/resume source text (with exact-option checks for selects). The extension independently refuses identity numbers, protected traits, credentials, OTP/CAPTCHA, signatures, attestations, consent, conflicts, citizenship/visa/export-control/clearance, criminal history, referrals, background/drug/health screening, compensation acceptance, checkboxes, and radio buttons. Prototype-pollution keys are discarded at both layers.
- Passwords, OTPs, CAPTCHA answers, provider tokens, raw prompts, resumes, and application contents are excluded from application logs. Newly touched CRM logs no longer include contact email or provider identifiers.
- Stripe and Tally webhooks fail closed on signature failure. Cron authentication fails closed if its secret is missing.
- API responses use no-store, no-sniff, no-frame, no-referrer, and API-only CSP headers. The site CSP now blocks objects, cross-origin framing, arbitrary form destinations, direct provider API connections, the old CORS proxy, and direct analytics-token delivery.
- Dependency versions are locked. The current production dependency audit reports zero known vulnerabilities.
- AI, job search, employer-feed discovery, subscription checks, access-code attempts, signup capture, analytics events, and CRM-stage changes now pass through a shared rate-limit boundary. In production it requires Upstash Redis plus a 32-byte hashing secret, stores only HMAC-pseudonymous account/IP keys, and fails closed when the store is absent or unreachable.
- Provider-facing routes enforce layered IP burst, account daily, and global weighted daily budgets. A separate Redis-atomic USD-cent ledger reserves approved worst-case exposure before each paid Job Agent boundary and fails closed on missing approval, category/global exhaustion, or unavailable persistence. The global budget values are server-only configuration and cannot be raised by browser input.
- Needs You email additionally fails closed without a signed Resend bounce/complaint webhook and an explicit bounded suppression-retention policy. The raw event body is signature/timestamp verified before parsing; fixed product and pseudonymous tenant tags must match the sender and recipient-derived tenant HMAC. Encrypted suppression records retain no recipient address, replayed event IDs are ignored, and the worker checks suppression before reserving monetary capacity or contacting Resend.
- Retention archival is a separate admin-only, explicit-confirmation boundary. Only an already verified, content-free signed audit head may leave the service. The exact-host HTTPS provider request is idempotent by audit digest and accepts no redirects or URL credentials. Readiness requires a reviewed legal-hold version, bounded retention, separate provider and acknowledgement secrets, a cryptographically verified lock acknowledgement, and recent independently retained scope-bound evidence; a generic successful response never establishes immutability.
- `npm run security:gate` performs a short-lived Redis write/read/delete probe and validates every required global budget without printing secret values. It must pass with production-scoped variables before an application deployment is approved.
- The Job Agent restore flow sets a host-only `Secure`, `HttpOnly`, `SameSite=Lax` opaque session cookie. The random token maps to a tenant-indexed AES-256-GCM record in Redis, expires after seven days, supports safe rotation plus current/all-device revocation, and is capped at 20 active device sessions per subject. The concierge neither receives nor forwards a bearer credential. Every Job Agent subscriber-data route requires the opaque session; a valid legacy bearer token is rejected with `SESSION_UPGRADE_REQUIRED`, and an invalid cookie never falls back to guest privileges. Existing bearer compatibility is isolated to the separate legacy resume product during its migration.
- Every encrypted persistence surface uses the shared versioned AES-256-GCM keyring. Production requires a safe non-secret active key ID; the active key plus no more than three prior decrypt-only keys are accepted. A schema-allowlisted maintenance tool performs dry-run verification by default and requires an exact confirmation for bounded atomic rewrites. It preserves TTLs, refuses version conflicts, and emits content-free totals/checkpoints only. The synthetic application-level restore drill is not evidence of provider backup retention or point-in-time recovery.
- `/api/account-data` provides one authenticated tenant-wide JSON export covering the applicant vault, campaign state, consent, schedule, Needs You notification preference, durable runs/packages, application checkpoints, value-free employer-browser task metadata, and redacted browser-handoff session summaries. Provider session references and generated document binaries are omitted. Every indexed operational collection is read in stable, cardinality-checked pages rather than silently capped at 500. The export includes content-free per-collection completeness counts; an index mutation, duplicate identity, early end, or collection above the controlled synchronous limit returns no file and `partialExportReturned: false`. Permanent Job Agent cloud deletion first requests provider-confirmed teardown for every tenant browser session. Confirmed sessions and their indexes are deleted; an unresolved provider session preserves its encrypted recovery reference and returns content-free partial-progress counts with `BROWSER_HANDOFF_CLOSE_RETRY_REQUIRED` before other account data is removed. A retry resumes from only the remaining sessions. After that preflight, deletion enumerates the exact tenant Blob prefix as well as the Redis object index, removes provider binaries before run metadata, sweeps the authoritative follow-up index before sessions, removes queue records and audit chains, clears bounded residual idempotency keys, then revokes every signed-user session. A failed provider listing or deletion stops before metadata removal, and every stage is retry-safe. Device-only data and separately retained billing, subscription, fraud-prevention, and legally required records remain outside that deletion.
- Consent revocation is an account-wide authorization stop, separate from device sign-out. The revoked consent record is durable before cleanup begins. Tenant-scoped queued/leased browser tasks are atomically cancelled, active runs/checkpoints/scheduling are paused, and provider sessions are closed before their encrypted recovery references are removed. Executing tasks retain their outcome-unknown recovery path and are never called cancelled; a content-free reconciliation flag tells the client cleanup is continuing. A revoked user cannot restore an existing provider session, and every worker rechecks current consent immediately before consuming a transmission approval.
- Action-time personal-data transmission and final-submission approvals expire after 15 minutes and are bound to the exact employer, requisition, document version, and scope hash. The isolated worker checks expiry again immediately before it consumes the single-use approval and before it loads confirmed candidate values. If a queued approval expires first, the session is durably returned to Needs You, the leased task is cancelled as pre-start with zero transmitted fields, and a new worker task can exist only after a later affirmative confirmation. If the session cancellation persists but the task cancellation write is interrupted, a later lease converges from the cancelled session checkpoint without starting the sandbox.
- `/api/job-agent-notifications` stores only an encrypted, versioned opt-in preference derived from the signed tenant. Browser input cannot choose a recipient. Fixed generic email copy excludes employer, job, action, and candidate data; pseudonymous idempotency/delivery markers are bounded and deletion-aware. A provider HTTP success means accepted only, never delivered or acted upon.
- Four Vercel Firewall rules are staged in observation-only mode for AI bursts, job/discovery bursts, write-route bursts, and common exploit probes. They are not live until separately reviewed and published.
- A shared controlled-beta launch manifest prevents the generic word `ready` from overstating capability. Signed beta requires counsel-approved versioned consent, encrypted durable storage, bounded scheduling, configured generic notifications/operator alerts, audit export, approved cost ceilings, an explicit 1-10 user pilot, pseudonymous tenant admission enforced within that exact bound, and named support/incident ownership. Delivery, recovery, backup/restore, browser-runner, and browser-session checks are accepted only as recent HMAC-signed envelopes that hash a retained operator artifact and bind to the exact active non-secret configuration. A signature protects integrity and scope; it does not replace independent observation or retained evidence. Pilot admission stores only 40-character HMAC tenant IDs, never candidate emails. It is checked for consent grants, signed-user work, and tenant-only background work; removing a tenant stops new/resumed work while preserving data and revocation controls. Package Ready additionally requires the isolated document renderer. Assisted application remains hard-disabled until the durable worker, snapshot-bound runner evidence, terms review, owner approval, and a resumable in-app browser-session handoff are all verified. Final submission remains hard-disabled pending separately approved execution and authoritative receipt capture.

## Application audit ledger

Application-session mutations create an atomic encrypted audit entry in the same Redis script as the session write. Entries commit the complete session version, form a SHA-256 chain, and are HMAC-signed with a key separate from the data-encryption key. Subscribers receive only the signed head/count; redacted ledger verification is restricted to server-confirmed administrators. The same admin boundary can produce a content-free head bundle signed with a third, dedicated export key; the bundle omits the session identifier, timeline, and candidate field values and is independently verifiable offline. Explicit candidate deletion removes the corresponding tenant ledger, while ordinary updates cannot overwrite prior entries. Production beyond the supervised beta still requires an approved retention-locked destination and tested backup/restore procedures; bundle authenticity alone is not WORM evidence.

## Prompt-injection containment

Employer pages, job descriptions, resumes, form labels, ATS responses, and model output are all untrusted data. They never grant authorization. The workflow uses layered containment:

1. The model receives a fixed task-specific system policy.
2. Sensitive secrets are rejected before and after the model call.
3. Model output is parsed, bounded, escaped, and schema-checked where structured output is required.
4. Deterministic code—not the model—decides which application fields are forbidden.
5. External transmission, employer-specific consent, signature, authentication, and final submission remain outside model authority.
6. Submitted status still requires authoritative employer receipt evidence.
7. The receipt-capture connector is exact-host, HMAC signed, redirect-blocked, and one-attempt only. Timeouts, conflicts, and provider failures require reconciliation and never imply submission.

Prompt injection cannot be made mathematically impossible. The safe design assumes the model can be manipulated and prevents its output from directly gaining privileges or causing irreversible actions.

## Production no-go gates

Do not launch this service broadly until all of these are complete:

- Configure a random 32-byte-or-stronger `TIER_SECRET`, exact `ALLOWED_EXTENSION_IDS`, webhook secrets, cron secret, and provider credentials in encrypted production settings; verify no preview inherits production secrets unnecessarily.
- Keep `JOB_AGENT_NEEDS_YOU_EMAIL_ENABLED=false` until the owner approves provider usage, the sending domain passes SPF/DKIM/DMARC review, bounce/complaint suppression and opt-out are verified, and a generic message reaches an approved synthetic mailbox. Never use candidate addresses for launch testing.
- Provision and bind Upstash Redis in Production and Preview, set a separate random `RATE_LIMIT_HASH_SECRET`, and exercise the Redis-backed path. Local development intentionally retains an in-memory fallback; production does not.
- Review the staged Vercel Firewall traffic, then advance each rule through preview enforcement and a separately approved production publish. Add managed bot rules only after verified-bot and legitimate automation behavior is known.
- The content-free operator alert adapter supports exact-host HTTPS allowlisting, bearer authentication, a versioned fixed-schema event contract, and a durable Redis outbox with contract-specific cooldown deduplication for readiness, audit-integrity, safety-control, global-budget, consequential-submission, authoritative-receipt, and queue-health events. The worker leases each alert, retries transient failures at bounded backoff with the same record-derived idempotency key, and dead-letters terminal failures after four attempts. Alert-delivery failure is recorded locally and never recursively pages through the same failed channel. Signed launch evidence binds to the endpoint, receiver contract version, and a deterministic fingerprint of the complete supported event set and delivery contract. It is disabled by default. Configure an approved destination and independently verify receiver-side idempotency, retry recovery, dead-letter observation, and handling of every current event before relying on it; a successful request alone is not proof of delivery.
- Independently exercise real-account expiry, device loss, restore, current-device logout, all-device logout, and cross-tenant denial during the supervised pilot. The Job Agent data plane now requires revocable opaque HttpOnly sessions; the wider legacy resume application retains bearer compatibility as a separate migration surface and cannot authorize Job Agent subscriber data.
- The primary `/concierge` and `/concierge.html` Job Agent routes now receive a separate fail-closed CSP with no `unsafe-inline` or `unsafe-eval`, no script/style attributes, self-only API connections, no frames, and self-only form actions. The embedded stylesheet and runtime style writes were replaced with external CSS, semantic progress elements, and state classes; the two fixed-version CDN document parsers have SHA-384 integrity pins. Desktop and mobile browser checks exercised the guided launch, My Jobs, and Needs You with the actual header and zero console warnings/errors. The wider legacy resume application still needs its separate `unsafe-inline` removal and full cross-site-scripting audit; its broader policy is not evidence for the Job Agent route.
- Move the implemented encrypted tenant stores to managed key rotation, independently exercise the account-wide export/deletion control with a supervised real account, export signed audit heads to retention-locked storage, and complete backup/restore and breach-response drills before expanding beyond the supervised cloud beta.
- Stripe webhook processing now requires a Redis-backed 90-second lease before any CRM or notification side effect. Records retain only a 64-character HMAC event reference, processing state, attempt count, and timestamps for 35 days; raw Stripe event IDs and customer data are not persisted in the idempotency record. Parallel deliveries return retryable failure while one lease is active, crashes release or age out safely, completed events return a duplicate success, and Resend receives a deterministic idempotency key for retry suppression. Signed-beta readiness fails closed unless a separate 32-byte-or-stronger `STRIPE_WEBHOOK_IDEMPOTENCY_SECRET` and durable Redis are configured. Stripe remains the source of truth for entitlement checks.
- Run passive and authenticated security scanning against an isolated staging deployment, including cross-tenant tests, CSRF, stored/reflected DOM XSS, OAuth lifecycle, webhook replay, file parsing bombs, rate-limit bypass, SSRF/DNS rebinding, and dependency/container scans. Do not run destructive active scans against production.
- Generated application DOCX/PDF files now pass bounded structural inspection and a fail-closed, exact-host malware-scanner contract before envelope-encrypted private object storage. Production provider configuration remains disabled pending approval and end-to-end synthetic verification. Uploaded source resumes still remain browser-local; any future server-side ingestion must use an isolated parser plus this scanner gate before persistence.
- The employer-browser candidate requires a reviewed snapshot plus exact runner version, SHA-256 digest, fixed runner path, budgets, a separate durable-execution switch, snapshot-bound evidence, terms review, and explicit assisted-pilot approval. Approved ordinary values are re-read from the encrypted vault only at execution time and cross-checked against the active fact version; the sandbox receives them through a random mode-0600 file, never command arguments. The encrypted task queue, value-free schema inspection, atomic reservation, single-use leases, stale-outcome reconciliation, account export/deletion, and key rotation are implemented. Production remains fail-closed until the external runner artifact and snapshot are independently verified and every manifest gate is satisfied.
- The first browser-extension release is built from an explicit file allowlist rather than packaging the source directory. Its reproducible archive excludes dormant multi-site filler modules and unsupported marketing/testing assets, loads no remote hosted presentation code, requests only the reviewed Greenhouse and 1stStep host permissions, and carries a per-file integrity manifest. Assisted launch requires the exact pinned archive SHA-256 in addition to supervised review approval; changing the artifact invalidates the controlled-beta release evidence.
- Before the Greenhouse extension can materialize any applicant-vault value, the server re-fetches the exact requisition from the reviewed employer feed. Closed or identity-changed roles finish as pre-submission Rejected/Closed with all open actions resolved, `personalDataTransmitted: false`, `submitted: false`, and `receiptVerified: false`. A transient or rejected feed response returns a retryable service failure without consuming the one-use sharing approval or loading candidate values.
- Complete privacy/legal review for applicant data, automated decision disclosures, terms, consent records, subprocessors, data residency, and employment-platform rules.
- The admin-only `/api/job-agent-operations` endpoint retains eight days of UTC daily counters for invalid authentication, rate-limit exhaustion, provider, discovery, durable-run, package, artifact-QA, application-session, audit-integrity, readiness, account-data, consequential-queue, and Stripe-webhook outcomes. Stripe counters distinguish completed, duplicate, retry-deferred, and failure without retaining event IDs or billing/customer values; processing failure also emits a generic critical operator alert. The schema is a fixed event allowlist, contains no subject, tenant, requisition, document, prompt, Stripe identifier, or candidate values, and is rendered only inside the server-confirmed admin audit console. An approved external incident destination and receiver-side alert verification remain required before widening the beta.

The authenticated account export also includes any tenant-linked Needs You email suppression status. That record is limited to the bounce/complaint reason, suppression timestamp, and `storesRecipient: false`; it never exports a recipient address or provider message body. Account deletion removes the same suppression record with the notification preference.

## External action boundary

The controlled Greenhouse extension can fill approved ordinary fields and attach the exact rendered résumé only after action-time transmission confirmation. It keeps field values and document bytes in memory, verifies document integrity before attachment, reports only field keys, and never clicks Submit. Account creation, credentials, OTP/CAPTCHA, identity verification, signatures, non-résumé uploads, and final submission remain human actions or independently disabled provider workflows. Cloud-browser activation still requires isolated per-tenant sessions, scoped credentials, resumable state, redacted audit records, terms/cost approval, and authoritative receipt verification.
